v1 is what deploys today, from the `main` branch. v2 runs in development on one machine, on draft pull requests, and no v2 component deploys. The rest of v2 is specified under [`/specs/`](/specs/). Everything in this documentation section describes v1 unless it says otherwise.

## Three states

| State             | What it covers                                                                                                                                                                                                                                                           |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploys today     | v1: the Dispatcher Worker, Workflows, Containers, the run catalog and check-run verdicts                                                                                                                                                                                 |
| In development    | `pnpm dogfood`, on the unmerged [#247](https://github.com/fractalboxdev/flare-dispatch/pull/247): this repository's CI through a local control plane under `wrangler dev`, the Rust device executor and a real lease, with the verdict read from the coordinator's record |
| Specified         | Placement deadlines, cloud fallback, spend, the GitHub path end to end, reclaim and job isolation on a device                                                                                                                                                             |

`pnpm dogfood` is not for production. Its jobs run on the host under your own user, which [MAMEKO-ISO-001](https://github.com/fractalboxdev/mameko/blob/8530203ba76ba00961e236b1fcea4f34b401bba1/specs/isolation-egress.md) forbids in a conformant deployment, and the `production` deployment refuses both the run and the software device key. It deploys nothing and posts nothing to GitHub.

## What v2 changes

v1 runs each job on Cloudflare. v2 is specified to run a job on hardware the organization owns first, keep Cloudflare as the control plane, and give the cloud only what owned capacity cannot claim before a deadline. The bet behind v2 is that a warm device reaches a verdict faster than a cold container; [phase 0](/specs/roadmap/) measures that bet before any later phase starts.

| Concern       | v1 (deploys today)                           | v2 (specified)                                                                                                                     |
| ------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Control plane | Dispatcher Worker and Cloudflare Workflows   | mameko's coordinator on `host-cloudflare`, with FlareDispatch's profile and GitHub appliers ([architecture](/specs/architecture/)) |
| Execution     | Cloudflare Containers                        | Owned devices, then Cloudflare Containers and outside launchers ([executors](/specs/executors/))                                   |
| Scheduling    | Per-pool admission slots, first in first out | Four classes, `release` to `batch`, with claim deadlines ([profile](/specs/profile/))                                              |
| Spend         | Per-execution cost metered on the dashboard  | A budget with a line per class, enforced at admission ([spend](/specs/spend/))                                                     |
| Run model     | Effect 3 programs in Cloudflare Workflows    | Effect 4 programs on mameko's workflow engine ([run model](/specs/run-model/))                                                     |

The right-hand column states target behaviour. A specification is written in the present tense, as a contract to implement and test against, so read it as what v2 must do, not what a deployment does today.

## What exists

- **Specifications.** Each area has a specification, and the [decision records](/specs/adr/) carry the reasoning. The [roadmap](/specs/roadmap/) assigns every requirement to one of five phases.
- **Implementation.** Draft pull requests hold the first v2 packages: the application profile and the check-run applier on [#246](https://github.com/fractalboxdev/flare-dispatch/pull/246), and the control plane, the run catalog and `pnpm dogfood` on [#247](https://github.com/fractalboxdev/flare-dispatch/pull/247). They are not merged into `main`, and no deployment runs them.
- **Gates.** A phase starts only after the gate of the phase before it passes. Phase 0's gate requires a warm run to reach its verdict at least 30% faster than the best cloud setup, and the roadmap's kill lines narrow the plan where a gate fails.

## Which section to read

Read [`/docs/`](/docs/) to deploy or operate FlareDispatch now. Read [`/specs/`](/specs/) to evaluate the v2 design, review a requirement or work on the implementation.
